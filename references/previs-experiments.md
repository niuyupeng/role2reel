# Whitebox and depth-reference experiments

Use when requested, after the scene/shot inputs relevant to the experiment are identified. Do not block an ordinary screenplay with these production stages. Source-truth, atomic-shot and physical/sound rules still apply. A provisional layout can be labeled an experiment; it must not be promoted to approved film direction.

## Whitebox

Pick one scene and one measurable spatial problem: doorway clearance, eyeline, occlusion, movement or camera axis. Use named dimensions, coordinate convention, actor/prop placeholders, camera lens and key positions, duration and the source shot revision. Inspect available Blender/runtime and current API documentation before code generation; do not claim it is installed or has rendered without checking.

Deliver the scene file or script plus a playable viewport/render preview and the actual camera/layout settings. Test start, transition and end states. Compare the preview with the original shot duty. Record what it proves about staging and what it does not prove about performance, final appearance or video-model adherence. Do not build fine assets before the spatial test is useful.

## Depth-reference A/B test

Keep one source interval, authorized target identity, output duration, backend/version and generation settings fixed as far as possible. Compare the raw reference arm with a depth-reference arm. Record model/license/source, actual preprocessing, normalized versus metric depth, near/far convention, per-frame normalization, temporal flicker and occlusion errors. Monocular depth is not an automatically clean 3D reconstruction or guaranteed removal of source identity.

Retain input/output hashes and compare geometry/movement, target identity, appearance leakage, temporal stability, repair time and cost. Do not present the resulting grayscale/depth map alone as proof that downstream video generation improved. If no approved generation backend, source media or budget is available, stop at the explicit missing dependency; do not invent results or spend on a provider by inference.

## Component reuse and product boundary

For a proposed external component, identify the exact missing function first. Verify its real repository, license, maintenance, dependencies, local data handling and one relevant sample before adopting it. Unclear spoken tool names remain unresolved; do not install a similarly named package by guess. Compare against the existing workflow rather than calling a fashionable component best.

Commercialization needs a distinct decision about customer, deliverable, data rights, support burden and measured cost. Meeting ideas about sales, tax or platform promotion are not established facts, signing authority or demonstrated demand. Keep paused account projects separate from reusable skill behavior.
