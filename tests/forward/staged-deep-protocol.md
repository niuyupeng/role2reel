# Staged deep end-to-end protocol

FT-09 through FT-12 are author-approved `light` unit fixtures. They test isolation, counterfactual logic, shared-context behavior, and outline-conflict handling from compact inputs. They do not show that a substantively reviewed deep biography was compiled into a scene.

FT-14 supplies that missing end-to-end test. A case definition is not a run. Execute it in a temporary project with actual files and retain `assets/templates/staged-life-path-eval.yaml` as the result record.

## Phase 1: admit an exact approved deep biography

Provide a populated workbench, its biography, and any project-level relationship ledger. The workbench must retain at least three independent root candidates, an author path-lock record bound to the fact-boundary and candidate hashes, and a `deep` biography meeting the content-sufficiency review in references/life-paths.md, without a default length quota. The biography needs its own author approval bound to that path context plus the exact biography revision and body hash; the path lock alone is insufficient.

Run the life-path audit with `--require-locked` and, when shared events exist, `--relationship-ledger`. Record the command, files, hashes, revisions, and result. Do not continue on an error.

## Phase 2: compile in an independent task

Start a fresh task with only locked source material. Compile character, cognitive-resource, memory, relationship, shared-context, and relevant outline-review assets. Record the exact audited workbench, approved biography, and any bound relationship ledger as hashed compile inputs. Every derived claim uses canonical `life-path:<branch>/<node>` source references. Record each actual artifact's project-root-relative path, type, file SHA-256, source closure, fact/candidate hashes, path revision, and biography revision/body hash in the workbench; the audit opens the exact files and validates those bindings and any shared events.

Reject any artifact that draws from a candidate or rejected branch. If formal scene or screenplay assets are requested, the current outline review must be clear or every hard conflict must have an author-approved resolution.

## Phase 3: isolate scene generation from the long biography

Start another fresh task. Give it the compiled runtime assets, current scene contract, and permitted outline state only. Do not provide the long biography, candidate workbench, rejected paths, earlier model transcript, or expected answer. This tests whether the compiled runtime carries the life into the scene instead of relying on hidden prompt access to the prose.

## Phase 4: controlled variants

Run and record each variant independently. Bind every run to its own hashed input set, canonical source closure, task ID, output file/hash, and blind output ID. `changed_inputs` names the corresponding audited `variant_context` field, not an informal label. A passing record rejects byte-identical outputs and a variant whose hashed inputs do not differ from the baseline; those checks establish only that something changed, not that the change is dramatically valid.

1. locked baseline;
2. different author-locked branch with the same fact-boundary hash, its own approved biography, audited workbench, compiled artifacts, and source closure;
3. different hashed occupational-context input while preserving the baseline candidate hash and compiled life assets;
4. removal of one named formative locked node in a separately locked/audited workbench, followed by recompilation;
5. dialogue-deletion pass bound to the exact baseline output hash while preserving strategy and state change.

Every claimed change in attention, appraisal, first impulse, relationship move, expression channel, or available means must cite the exact baseline or variant runtime claim and causal node that produced it. The trace record binds both run task IDs and both actual output hashes. An untraceable difference fails; identical results after branch swap or node ablation require review rather than a success claim.

## Phase 5: blinded human review

Randomize outputs and hide workflow, character names when the metric requires it, and generation order. Map every anonymized ID one-to-one to an actual run output and cover all five IDs in the recorded playability, identifiability, relationship, nonverbal, and read-aloud reviews. Review causal individuality, semantic branch leakage, character identifiability, actor playability, relationship truth, nonverbal substitution, read-aloud naturalness, and repair burden. Automated checks can verify files, hashes, revisions, explicit references, output-ID coverage, and declared leakage. They cannot prove causal density, semantic isolation, reviewer independence, or whether an actor can play the scene.

Every reviewed output records an explicit positive or negative verdict/status plus concrete evidence. A numeric rating may accompany that verdict, but a rating alone has no declared pass threshold and cannot authorize `behavior_pass: true`.

Leave `behavior_pass: false` while any actual artifact, staged run, traceability decision, or blinded review is missing. When the record is complete, run `python scripts/audit_staged_eval.py <record.yaml>`; it re-runs the mechanical life-path audit and refuses incomplete or hash-mismatched passing records. This is still record-integrity evidence, not proof of execution truth or artistic success. Store large biographies and run outputs in the temporary project or ignored `test-results/`, not in the skill package.
